# GPUVerify Analysis — TVM Issue #10210

## Bug Summary

TVM's `s[op].parallel(axis)` accepts any loop axis — including reduction
axes — without validation. When a reduction axis `k` is parallelised, TVM's
runtime launches independent CPU OpenMP threads for each k iteration. All
threads perform a non-atomic read-modify-write on the same accumulator
`C[i][j]`, producing a WAW (write-write) race and silently wrong results.

---

## Important: CPU Race vs GPU Race

### Where does the race actually happen?

In the real bug, the race happens entirely on the **CPU**:
```
CPU OpenMP threads (64 threads, one per k)
         ↓
C[i*64+j] = C[i*64+j] + A[i*64+k] * B[k*64+j]
         ↑
CPU RAM (not GPU memory)
```

TVM's `parallel()` on the reduction axis generates CPU code like:
```c
// CPU code generated by TVM (not CUDA)
#pragma omp parallel for
for (int k = 0; k < 64; k++) {
    C[i*64+j] = C[i*64+j] + A[i*64+k] * B[k*64+j];  // WAW on CPU RAM
}
```

**No CUDA kernel is generated.** The computation runs on CPU threads
accessing CPU RAM — not on GPU threads accessing GPU memory.

### Why does this matter?

GPUVerify, Faial, and Weft all require a CUDA kernel (`.cu` file) as input.
Since TVM generates CPU code for this bug, there is nothing for these tools
to directly analyze.

### Is it still a data race?

**YES** — by definition:
- Multiple threads ✅
- Same memory location (`C[i*64+j]`) ✅
- At least one write ✅
- No synchronisation ✅

The race pattern is identical to a GPU data race — just running on different
hardware (CPU threads instead of CUDA threads).

## CUDA Kernel (Manually Written)

Since no CUDA kernel is generated by the bug, we manually wrote a CUDA
kernel that models the exact same race pattern — replacing CPU OpenMP
threads with CUDA threads, and CPU RAM with GPU global memory:
```cuda
__global__ void parallel_reduction_buggy(float* C, float* A, float* B) {
    int k = threadIdx.x;  // 64 threads, one per k iteration
    int i = 0, j = 0;

    /* BUG: all 64 threads read and write C[0] simultaneously
     * Thread 0: C[0] = C[0] + A[0]*B[0]
     * Thread 1: C[0] = C[0] + A[1]*B[64]  <- reads same stale C[0]
     * ...
     * Last writer wins -> 63 updates lost -> wrong result */
    C[i*64+j] = C[i*64+j] + A[i*64+k] * B[k*64+j];
}
```

This is **not** the actual CUDA code generated by TVM — it is a manual
translation of the buggy TIR pattern into CUDA to enable GPUVerify analysis.
The actual bug runs on CPU threads, but the race pattern is identical.

## GPUVerify Result

**RACE DETECTED — 2 errors**
```
error: possible read-write race on C[0]:
  Write by thread 0: C[i*64+j] = C[i*64+j] + A[i*64+k] * B[k*64+j];
  Read  by thread 1: C[i*64+j] = C[i*64+j] + A[i*64+k] * B[k*64+j];

error: possible write-write race on C[0]:
  Write by thread 0: C[i*64+j] = C[i*64+j] + A[i*64+k] * B[k*64+j];
  Write by thread 1: C[i*64+j] = C[i*64+j] + A[i*64+k] * B[k*64+j];

GPUVerify kernel analyser finished with 0 verified, 2 errors
```

GPUVerify correctly identifies both the read-write and write-write races
on `C[0]` — all 64 threads read the same stale value and write back
their partial sum with no synchronisation.

## Key Explanation for Why CPU, Not GPU

| Aspect | TVM #10210 (this bug) | Typical GPU race |
|--------|----------------------|------------------|
| Thread type | CPU OpenMP threads | CUDA threads |
| Memory | CPU RAM | GPU global/shared memory |
| Sync primitive | `omp barrier` | `__syncthreads()` / `atomicAdd` |
| Tool applicable | No (CPU race) | Yes (GPU race) |
| Race pattern | Identical WAW/RAW | Identical WAW/RAW |

The race pattern is the same — only the hardware differs. The CUDA kernel
we wrote models this pattern faithfully, and GPUVerify detects it correctly.

---

## Root Cause

`src/te/schedule/schedule_lang.cc` — `Stage::parallel()` does not validate
whether the target axis is spatial or a reduction axis before marking it
`ForKind::kParallel`. The CPU thread pool in `src/runtime/thread_pool.cc`
then launches independent threads for each k-iteration, all performing
non-atomic RMW on the same output element.
