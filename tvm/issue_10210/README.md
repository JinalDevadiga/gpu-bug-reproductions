# Issue #10210 — Silent Wrong Results When `parallel()` Applied to Reduction Axis

## Source
- **GitHub Issue:** https://github.com/apache/tvm/issues/10210
- **Reproduced on:** apache-tvm 0.11.1, Python 3.10, Ubuntu/WSL2 (CPU only)
- **Status:** Open

## What is the Bug?

TVM's TE scheduling API allows `s[op].parallel(axis)` to be called on any
loop axis — including **reduction axes**. When a reduction axis is
parallelised, multiple OS threads each compute a partial sum and write back
to the **same output element** `C[i][j]` without any atomic operation or
barrier:

```
parallel for k in range(K):       // <- race: multiple threads
    C[i][j] += A[i][k] * B[k][j] // write same accumulator
```

This is a **WAW (write-write) data race** on the accumulator. Partial
products from competing threads are silently overwritten and lost, producing
a numerically wrong result. TVM compiles and runs the kernel to completion
with **no warning or error** of any kind.

## Root Cause

`src/te/schedule/schedule_lang.cc` — `Stage::parallel()` does not check
whether the target axis is a spatial or reduction axis before marking it
`ForKind::kParallel`. The threadpool then launches independent threads for
each k-iteration, all performing non-atomic read-modify-write on the same
output element.

## Why This Was Initially Marked "Not Applicable" — And Why We Updated It

### Original reasoning (why we said N/A):

TVM's `parallel()` on a reduction axis does **not** generate a CUDA kernel.
Instead, TVM generates CPU code where OS threads access CPU RAM:

```c
// What TVM actually generates — CPU code, NOT CUDA
#pragma omp parallel for
for (int k = 0; k < 64; k++) {
    C[i*64+j] = C[i*64+j] + A[i*64+k] * B[k*64+j];  // WAW on CPU RAM
}
```

Since GPUVerify, Faial, and Weft all require a CUDA kernel (`.cu` file)
as input, we initially concluded there was nothing to analyze.

### Why that reasoning was incomplete:

The race pattern is **identical** to a GPU data race — multiple threads,
same memory location, at least one write, no synchronisation. Following
mentor feedback, we manually wrote a CUDA kernel modeling the same pattern.

### The CUDA model:

```cuda
__global__ void parallel_reduction_buggy(float* C, float* A, float* B) {
    int k = threadIdx.x;  // 64 CUDA threads, one per k iteration
    int i = 0, j = 0;

    /* BUG: all 64 threads read and write C[0] simultaneously
     * Thread 0: reads C[0]=0, computes 0+A[0]*B[0],  writes back
     * Thread 1: reads C[0]=0 (stale!), computes 0+A[1]*B[64], writes back
     * Last writer wins -> 63 updates lost -> wrong result */
    C[i*64+j] = C[i*64+j] + A[i*64+k] * B[k*64+j];
}
```

This is **not** the actual code TVM generates — it is a faithful manual
translation of the buggy TIR pattern into CUDA to enable static analysis.

---

## CPU Race vs GPU Race — Key Distinction

| Aspect | TVM #10210 (real bug) | Our CUDA model |
|--------|----------------------|----------------|
| Thread type | CPU OpenMP threads | CUDA threads |
| Memory | CPU RAM | GPU global memory |
| Sync needed | `omp atomic` | `atomicAdd()` |
| CUDA kernel generated? | ❌ No | ✅ Yes (manually written) |
| Race pattern | WAW/RAW on C[i][j] | WAW/RAW on C[i][j] |
| Race detectable? | Not by GPU tools directly | ✅ Yes by GPUVerify and Faial |

#### Why Weft Missed This Bug

The race in our CUDA model is on **global memory** — all 64 threads write
to `C[i*64+j]` which is a global memory array passed as a kernel parameter.
Weft only analyzes **shared memory** accesses (`ld.shared`/`st.shared` in
PTX) and has no visibility into global memory whatsoever.

`Shared Memory Locations: 0` and `Total Race Tests: 0` confirm Weft found
nothing to analyze — the kernel contains no shared memory accesses at all.
This is the same fundamental scope limitation as Triton #4233 and #7402 —
global memory races are completely invisible to Weft by design.
