# Issue #10210 — Tree Reduction with Shared Memory Buggy When `threadIdx.y` Present

## Source
- **GitHub Issue:** https://github.com/apache/tvm/issues/10210
- **Reproduced on:** apache-tvm 0.11.1, Python 3.10, Ubuntu/WSL2
- **Status:** Closed (Fixed in PR #10207)

## What is the Bug?

TVM's CUDA code generator incorrectly assumes that a tree reduction fits
within a single warp when `blockDim.x` is not a multiple of warp size (32).
It skips `__syncthreads()` between reduction steps inside the
`if (threadIdx.x < N)` block.

When `threadIdx.y` is also active, threads span **multiple warps** — so
`__syncthreads()` IS required between each reduction step. Without it,
threads from one reduction step read shared memory that other threads from
the previous step are still writing — a shared memory race condition.

## The Buggy Generated CUDA Code

From the GitHub issue — actual kernel generated by TVM:
```cuda
if (((int)threadIdx.x) < 8) {
    red_buf0[threadIdx.y*26 + threadIdx.x] +=
        red_buf0[threadIdx.y*26 + threadIdx.x + 8];
    // BUG: MISSING __syncthreads() here!

    red_buf0[threadIdx.y*26 + threadIdx.x] +=
        red_buf0[threadIdx.y*26 + threadIdx.x + 4];
    // BUG: MISSING __syncthreads() here!

    red_buf0[threadIdx.y*26 + threadIdx.x] +=
        red_buf0[threadIdx.y*26 + threadIdx.x + 2];
    // BUG: MISSING __syncthreads() here!

    red_buf0[threadIdx.y*26 + threadIdx.x] +=
        red_buf0[threadIdx.y*26 + threadIdx.x + 1];
}
```

## Why blockDim.x=26 Triggers the Bug

| blockDim.x | Multiple of 32? | Fits in one warp? | Bug triggers? |
|-----------|----------------|-------------------|---------------|
| 32 | ✅ Yes | ✅ Yes | ❌ No |
| 26 | ❌ No | ❌ No — spans 2 warps | ✅ Yes |

TVM assumed `blockDim.x=26` fits in one warp so warp-level synchronization
is enough. But with `threadIdx.y` active and `blockDim.x` not a multiple
of 32, threads span two warps — explicit `__syncthreads()` is required
between every reduction step.

## The Fix (from PR #10207)

Add `__syncthreads()` between each reduction step:
```cuda
if (threadIdx.x < 8) {
    red_buf0[...] += red_buf0[... + 8];
}
__syncthreads();   // <- added
if (threadIdx.x < 4) {
    red_buf0[...] += red_buf0[... + 4];
}
__syncthreads();   // <- added
// ... and so on
```

## Important Note on reproduce.py

The TVM pip wheel (`apache-tvm==0.11.1`) does not include CUDA codegen
(`target.build.cuda is not enabled`). Therefore we cannot regenerate the
buggy kernel from Python. Instead, `kernel_clean.cu` uses the **actual
buggy CUDA kernel directly from the GitHub issue** — this is the real
kernel TVM generated on the reporter's machine, not a manually written model.

#### Why GPUVerify detected it:

Inside `if (threadIdx.x < 8)`, thread (6,13,0) writes `red_buf0[344]`
at stride-8 step while thread (2,13,0) is still reading `red_buf0[344]`
at stride-4 step — no `__syncthreads()` between them. GPUVerify correctly
identifies all 5 missing barrier violations.

## Root Cause

`src/tir/transforms/lower_thread_allreduce.cc` — TVM's tree reduction
lowering did not check whether `blockDim.x` is a multiple of warp size
before assuming warp-level synchronization is sufficient. When `threadIdx.y`
is active and `blockDim.x=26` (not a multiple of 32), threads span multiple
warps and explicit `__syncthreads()` is required between each reduction step.
Fixed in PR #10207 by adding warp-alignment check before omitting barriers.
